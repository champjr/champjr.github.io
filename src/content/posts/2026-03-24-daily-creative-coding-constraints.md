I used to think “constraints” were the thing you worked around on the way to “the real idea.” Like: if only I had more time, more features, more libraries, more horsepower, more screens, more everything—*then* I’d make the good version.

Now I’m pretty convinced the opposite is usually true: constraints are not a tax you pay to get to creativity. They’re the handle creativity grabs.

And it’s not just an artsy pep talk. The same logic quietly makes software tools nicer to use (and teams nicer to work with). The right constraints turn a foggy “I could do anything” into a concrete “I can do *this* next.”

## The blank canvas is not neutral

A blank canvas sounds romantic. In practice it’s a productivity prank.

When everything is possible, you spend your first hour shopping for possibility:

- Which framework? Which theme? Which starter?
- Should I refactor before I start? (You already know the answer is “yes,” which is also the problem.)
- Should it be minimal, maximal, playful, serious, generative, interactive, audio-reactive, data-driven…

The blank canvas doesn’t say “create.” It says “decide.”

Constraints reduce decisions. That’s their whole magic trick.

## Creative coding: where constraints are the point

If you’ve ever played with creative coding—sketching with code the way you might doodle with a pen—you’ve probably felt this.

A “sketch” works because it’s *allowed* to be small.

- 300 lines, not 3,000.
- One visual idea, not a product.
- A single afternoon, not a roadmap.

That’s why environments like p5.js are so approachable: they nudge you into a constrained loop—draw something, run it, tweak it, repeat.

Useful link (if you want to try it): p5.js has a friendly “get started” path that’s basically a constraint in documentation form.

<https://p5js.org/get-started/>

The constraint isn’t “you must use JavaScript.” The constraint is “you are here to make a small thing quickly.”

## Constraints that actually help (and the ones that don’t)

Not all constraints are good constraints.

Good constraints:

- **Limit scope without limiting curiosity.** “One mechanic” is good. “No exploration” is not.
- **Are easy to explain.** If you can’t summarize the constraint, you’ll forget it mid-way and drift.
- **Create a finish line.** You should be able to ship *something* even if it’s ugly.

Bad constraints:

- **Hide the finish line.** “Make it great” is not a constraint; it’s a threat.
- **Increase tool friction.** If the constraint is “fight the build system,” you’re not creating—you’re paying rent.
- **Are unchosen.** The constraint you pick has motivational power. The one that shows up as a surprise invoice does not.

There’s a useful mental reframe here: constraints are a design surface. You can tune them.

## A few constraints I’ve learned to like

These are small, practical constraints that tend to produce real output.

### 1) Timebox the first draft

I like the rule: *first draft in 30–60 minutes, even if it’s embarrassing.*

Embarrassment is a feature. If you’re not slightly embarrassed by the first draft, it probably took too long.

The goal of the first draft is not quality. It’s to create a *shape* you can improve.

### 2) Use a single “accent color” in a project

In visuals, unlimited color palettes create unlimited indecision.

Pick one accent color and let everything else be grayscale (or near-grayscale). Now your design decisions have gravity:

- Is this important enough to deserve the accent?
- If everything is accented, nothing is.

This works for UI, slides, and generative art. It also works for writing: pick one strong theme and let everything else support it.

### 3) Pick a small set of primitives

When you code visuals, you can constrain yourself to a few shapes or operations:

- circles + lines only
- noise + threshold only
- rectangles + rotation only

This sounds restrictive until you watch your brain start doing something fun: it explores the space *inside* the restriction.

Constraints turn “What should I do?” into “What can I do *with this*?”

That question is rocket fuel.

### 4) Ship a “bad version 1”

I’m a fan of deliberately shipping a “bad version 1.” Not sloppy. Just honestly minimal.

- “It works, but it’s not pretty.”
- “It’s readable, but not optimized.”
- “It’s one scene, not a whole app.”

The constraint is: **you’re not allowed to solve every problem in version 1.**

That’s not lowering standards. It’s sequencing them.

### 5) Make the toolchain boring

This might be my most opinionated one: if the *project* is experimental, the toolchain should be boring.

You can be adventurous in one dimension at a time:

- new visual idea + boring build
- new library + boring design
- new architecture + boring UX

When everything is new, you can’t tell what’s failing.

Constraints don’t just help you create; they help you debug.

## The hidden benefit: constraints create a record of intent

Here’s the part I didn’t expect.

A good constraint doubles as documentation.

If I open a folder six months later and it says, implicitly:

- “This was a one-hour sketch”
- “This used only circles and lines”
- “This was a one-color experiment”

…then I don’t judge it like a product. I judge it like a sketch. It’s immune to the “why didn’t I finish this?” guilt spiral.

Constraints make your past self look more reasonable.

That’s surprisingly valuable.

## A tiny constraint to try today

If you want something concrete, try this:

1. Pick a subject: “rain,” “grids,” “small sadness,” “airport carpets,” whatever.
2. Pick exactly two primitives (shapes, sounds, words—anything).
3. Give yourself 45 minutes.
4. Ship the result somewhere: a gist, a folder, a screenshot, a note.

The goal is not to impress anyone.

The goal is to re-teach your brain that output is a *procedure*, not a mood.

And constraints are part of the procedure.

They’re not the enemy of creativity.

They’re the door.
